## T1 分析結果 — JWT Secret 強度審查

**時間**: 2026-04-10T01:12:00Z  
**狀態**: 🔄 失敗（需修復）

### 🔍 發現

**1. JWT Secret 定義** (`auth-service/src/index.js`)
```javascript
const JWT_SECRET = process.env.JWT_SECRET || 'super-secret-openclaw-key-change-me-in-prod';
```

`.env.example` 中實際值同樣是：`JWT_SECRET=super-secret-openclaw-key-change-me-in-prod`

### ⚠️ 嚴重問題

**問題 A：使用預設 Secret（推測攻擊風險極高）**
- 攻擊者若知道此默認值，可偽造任意 JWT token（role: admin）
- 達成條件：演算法為 HS256 + 攻擊者知曉 secret
- 實務上：`.env.example` 發佈於公開 repo，secret 為已知字串

**問題 B：Secret  entropy 不足**
- `super-secret-openclaw-key-change-me-in-prod` 為自然語言語句
- 長度 47 字節，但可預測性高（雜湊空間遠小於隨機 256 位元）
- 使用 `jsonwebtoken` library，HS256 預預設即可被暴力破解

**問題 C：無 Algorithm 限制（Algorithm Confusion Attack）**
```javascript
jwt.verify(token, JWT_SECRET)
```
代碼未指定 `algorithms: ['HS256']`，攻擊者可透過 `alg: RS256` + 公共 RSA 密鑰進行混淆攻擊。

**問題 D：無 secret 長度強制驗證**
- 未檢查 `JWT_SECRET` 是否 >= 256 bits
- 空值或過短 secret 不會被拒絕

### ✅ 良好實踐（已存在）

1. ✅ 每個 Access Token 有 `jti`（JWT ID）支持黑名單
2. ✅ Refresh Token 使用一次性旋轉（Rotation）
3. ✅ Token TTL 合理（Access: 24h, Refresh: 7 days）
4. ✅ 支援 Token 黑名單（Redis）

### 🛠️ 修復建議

1. **強制使用強 secret**：啟動時若 `JWT_SECRET` 為預設值則拒絕啟動
2. **限制 Algorithm**：在 `jwt.verify()` 中明確指定 `algorithms: ['HS256']`
3. **增加 secret 複雜度**：使用 `crypto.randomBytes(64).toString('hex')` 生成
4. **添加 secret 輪換機制**：支援多版本 secret（支援舊 token 寬限期）

### 📋 驗收標準

- [✅] 啟動時若使用預設 secret，進程 abort 並顯示明確錯誤
- [✅] `jwt.verify()` 明確指定 `algorithms: ['HS256']`
- [✅] 建議：透過 `crypto.randomBytes(32)` 強制生成 256-bit 隨機 secret

## T7 修復結果 — 2026-04-10T18:29:00Z

**狀態**: ✅ 完成

### 🔧 新增檔案

#### 1. `scripts/key-rotation.js` — 主輪換腳本
**功能**：
- `generateKey()` — 生成 48 位元組隨機 master key（格式：`sk-{hex}`）
- `hashKey()` — SHA256 前 16 字元（只用於識別，不暴露 key）
- Redis 存儲結構：
  - `litellm:keys:active` — 當前活躍 key（JSON: `{key, hash, created_at}`）
  - `litellm:keys:versions` — 有序集合（score=時間戳，member=hash）
  - `litellm:keys:info:{hash}` — Hash 類型（prefix, created_at, expires_at, predecessor）
  - `litellm:keys:grace:{hash}` — 字符串，TTL=24h（寬限期過期時間戳）
- `rotateKey()` 流程：
  1. 檢查上一 key 是否在寬限期（是則略過）
  2. 生成新 key，計算 hash
  3. 舊 key 寫入 `grace:*`（TTL=24h）
  4. 新 key info 寫入 Redis
  5. 更新 `active`
  6. 寫入版本歷史（zadd）
  7. 清理超出的歷史版本（保留最近 5 個）
  8. 更新 `.env` 中的 `LITELLM_MASTER_KEY`
  9. 執行 `docker compose restart litellm`

**用法**：
```bash
node scripts/key-rotation.js --rotate   # 執行輪換
node scripts/key-rotation.js --status   # 查看狀態
node scripts/key-rotation.js --validate <key>  # 驗證 key
```

#### 2. `key-rotation-validate.js` — Key 驗證中間件
**功能**：
- `validateMasterKey(key)` — 驗證 key 是否活躍或寬限期內
- `getRotationStatus()` — 獲取輪換狀態摘要
- `middleware()` — Express/Koa 風格中間件
- 支援兩種 header：`x-api-key` 或 `authorization: Bearer {key}`
- 失敗時保守返回無效（安全預設）

#### 3. `scripts/key-rotation.service` + `scripts/key-rotation.timer`
**功能**：Systemd 計時器，每 7 天自動執行輪換
- Timer: `OnCalendar=*-*-* 03:00:00` + `Interval=7d`
- Service: Type=oneshot，執行 `node scripts/key-rotation.js --rotate`
- 安全加固：NoNewPrivileges=true, PrivateTmp=true
