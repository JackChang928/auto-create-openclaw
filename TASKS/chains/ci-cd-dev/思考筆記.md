## 2026-04-10T18:41Z — T3 完成

### 完成內容
- **新增 `docker-build` job**：於 `.github/workflows/ci.yml`，依賴 `build` job
- **Job 觸發條件**：`github.event_name == 'push' && (branch main OR tag)`，不影響 PR 流程
- **Docker images 建置**（3個）：
  1. `auto-create-openclaw`（main app）- 新建 `Dockerfile`，node:20-alpine + non-root user
  2. `auth-service` - 使用既有的 `auth-service/Dockerfile`
  3. `billing-service` - 使用既有的 `billing-service/Dockerfile`
- **Image registry**：GHCR（`ghcr.io/${{ github.repository }}/`）
- **Tagging 策略**：main app 使用 semver + sha + branch；services 使用 sha + latest
- **Docker BuildKit** 搭配 `cache-from: type=gha` / `cache-to: type=gha,mode=max`（GitHub Actions cache）
- **本地驗證**：3 個 image 全部 build 成功 ✅

### 分析
- 這個 monorepo 有 3 個獨立可部署的 service（main app + 2 microservices）
- 採用 GHCR 而非 Docker Hub（免費、與 GitHub Actions 原生整合）
- docker-build job 加在 lint → typecheck → build pipeline 末端，確保代碼品質才建 image
- 3 個 service 的 image tags 策略：
  - Main app：`sha-{short}`（每次部署可追溯）、`latest`（最新）、semver tag（穩定版本）
  - Services：`{sha}` + `latest`（簡化策略，因為 services 變動頻率低）

## 2026-04-10T18:59Z — T4 完成

### 完成內容
- **整合 Trivy 漏洞掃描**：將 `trivy-scan` job 整合到 `docker-build` job 內部（重新命名為 `Docker Build & Scan`）
- **為何不走獨立 job**：若 Trivy 以獨立 job 運行，需額外向 GHCR 拉取 image，且需要 `packages: read` 權限 + `docker/login-action`。整合進 `docker-build` job 可直接 scan 本地建置的 image，零額外認證成本
- **Job 權限**：`security-events: write` 用於上傳 SARIF 到 GitHub Security tab
- **掃描範圍**：CRITICAL + HIGH 漏洞（跳過 MEDIUM/LOW/UNKNOWN 避免噪音）
- **SARIF 上報**：透過 `github/codeql-action/upload-sarif@v3` 一次性上傳 3 個 image 的結果到 GitHub Security tab（"Security" > "Vulnerability alerts"）
- **本地驗證**：Trivy v0.69.3 scan `auto-create-openclaw-base:latest` 發現多個 HIGH severity：
  - `CVE-2026-26960/29786/31802`：node-tar 路徑穿越漏洞
  - `CVE-2026-39363/39364`：Vite 開發服務器資訊洩露

### 分析
- Trivy 的 SARIF 格式讓 GitHub Actions 可以直接追蹤漏洞趨勢（而非只在 CI log 中看到）
- 這次發現的漏洞主要來自 `node:20-alpine` base image（node-tar），這是 Node.js 官方 base image 的已知問題，短期内無法完全避免
- 可考慮的方向：
  1. 切換到 Distroless / Chainguard images 减少 base image 漏洞面
  2. 在發現 CRITICAL 時 blocking pipeline（目前設為記錄未 blocking）
  3. 將 trivy 替換成 `grype`（更快的漏洞資料庫更新）

## 2026-04-10T19:14Z — T5/T6 完成（deploy-staging + deploy-production）

### 分析

Phase 2 CD 的最後兩塊積木：staging 部署（main push）和 production 部署（tag push）。

**部署架構選擇**：專案使用 docker-compose，無 Kubernetes。Server 是 remote machine，需要 SSH 部署。`appleboy/ssh-action` 是 GitHub Actions 生態中最受歡迎的 SSH action，可直接在 workflow 中執行遠端腳本。

**Image Tag 策略**：
- staging：`ghcr.io/<repo>/auto-create-openclaw:<sha>` — 每次 main push 都不同，精確對應 commit
- production：`ghcr.io/<repo>/auto-create-openclaw:<tag>` — semver tag，穩定可重現

**docker-compose.prod.yml**：deployment script 透過 `sed -i` 動態替換 image tag，而非 hardcode，確保 production server 上的 compose file 永遠反映最新部署版本。

**GitHub Environments**：deploy-staging 和 deploy-production 分別綁定 `staging` / `production` environment，可額外設定 protection rules（required reviewers, wait timer）。需在 repo settings → environments 預先建立。

**安全性考量**：
- SSH private key 存於 GitHub Secrets，不進 repo
- `appleboy/ssh-action` 支持 `ssh-keyscan` 自動 trust server host key
- GHCR login 用 `GITHUB_TOKEN`（標准 secret），packages: read 權限足夠 pull
- `sed -i` 替換 image 有 `|| true` fallback，萬一 compose file 格式不同不會卡住

### 待確認

1. **GitHub Environments** 尚未在 repo 設定，需手動建立 `staging` 和 `production` environments
2. **Vars**（STAGING_HOST, PRODUCTION_HOST 等）需在 repo → Settings → Variables 設定
3. **Secrets**（SSH private keys）需在 repo → Settings → Secrets and variables → Actions 設定
4. Server 上的 `~/auto-create-openclaw-prod/docker-compose.prod.yml` 需手動建立一次（用 `deploy/standalone/docker-compose.prod.yml` 為範本）
5. production deploy 中 `sed -i` 的 image 替換正則可能需根據實際 compose file 調整
